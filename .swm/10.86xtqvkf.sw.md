# Refactoring Plan

## Objective

Reduce coupling and clarify ownership without changing legal-data semantics,
public behavior, provenance, or evidence offsets. Refactoring is successful
when the code is easier to locate and test, not merely when files are smaller.

## Order Of Work

1. Establish a clean baseline: collection, focused tests, diagnostics, and current generated docs.
2. Separate route registration, API handlers, query helpers, and page rendering from `backend/routes.py`.
3. Clarify database/model ownership while preserving ORM imports and migration behavior.
4. Isolate ingestion adapters from canonical merge policy.
5. Isolate extraction candidates, normalization, persistence, and resolution.
6. Add browser smoke coverage before moving embedded UI code.
7. Add data-quality and performance gates before corpus-scale changes.
8. Introduce the manager-agent scaffold only after ownership and evidence rules are stable.

## Refactor Unit

Each change must name one owning module, one behavior expectation, one dependency
boundary, one focused check, and one rollback path. Move one cohesive route,
helper, or page builder at a time. Preserve compatibility wrappers temporarily
when callers are numerous, then remove them only after references and tests are
clean.

## Do Not Break

## Current Coupling Map

| Surface | Why it is large | First safe seam | Main acceptance risk |
| --- | --- | --- | --- |
| `backend/routes.py` | API, SQL orchestration, analytics, generated UI | one route family and mapper | response or browser drift |
| `backend/database.py` | settings, engine, ORM, initialization | settings/session versus models | migration/import drift |
| `backend/ingestion.py` | source normalization and canonical merge | adapter output versus merge policy | provenance/identity loss |
| `backend/citations.py` | rules, normalization, resolution, persistence, metrics | candidate extraction versus resolution | exact span/layer drift |
| page modules | HTML, CSS, JavaScript | one active page family | runtime interaction failure |

## Refactor Sequence Per Module

1. Inventory symbols, callers, side effects, and current tests.
2. Add or improve a characterization check before moving code.
3. Extract one cohesive responsibility behind a stable interface.
4. Keep a compatibility import or wrapper while callers migrate.
5. Run the focused check immediately, then inspect generated references.
6. Remove obsolete forwarding only after repository-wide references are clean.

Do not combine a structural move with a semantic rule change, schema migration,
or broad formatting rewrite. Those changes need separate evidence and rollback.

- Separate case citations, statute references, metadata, tags, and embeddings.
- Backend-owned source/chunk offsets and exact evidence spans.
- Explicit source provenance and merge priority.
- IRPA/IRPR nested provision coverage such as `34(1)(f)`.
- Active `/data-explorer` behavior and legacy redirect boundaries.
- Side-project isolation and bounded overnight operations.


## First Refactor Candidates

The safest first candidates are cohesive, well-tested route families and page
builders. Avoid beginning with a broad rename of ORM classes, extraction regex
rewrites, or database migrations. Those surfaces have higher semantic and
operational blast radius and require stronger fixtures and rollback evidence.

## Completion Gate

No refactor is complete until focused tests pass, touched modules compile,
generated references are refreshed, active UI behavior is checked when relevant,
and `SYSTEM_REFERENCE.md`, this plan, and affected Swimm walkthroughs agree.
