# Project Manager Agent Workflow

## Mission

The project-manager agent coordinates bounded, evidence-backed engineering
work. It does not invent legal conclusions, silently change architecture,
replace human review, or mark incomplete validation as successful.

## Required Task Record

```text
Task:
Why now:
Owner surface:
Dependencies:
Risk boundary:
Smallest falsifiable check:
Acceptance criteria:
Docs/generated references:
Rollback/recovery:
Evidence:
```

## Manager Loop

1. Read the Overview, System Map, Refactoring Plan, `SYSTEM_REFERENCE.md`, and relevant canonical docs.
2. Identify one owning surface and one falsifiable behavior expectation.
3. Check worktree state and avoid disturbing unrelated user changes.
4. Assign one implementation slice with a focused validation command.
5. Require test, compile, browser, API, or bounded operational evidence according to risk.
6. Update affected source documentation and Swimm walkthroughs in the same checkpoint.
7. Record blockers, residual risks, and known unrelated failures explicitly.

## Work Classification

| Class | Required coordination |
| --- | --- |
| Code refactor | Owner, callers, focused tests, compatibility plan |
| Schema change | ORM/API/migration alignment, upgrade/rollback, schema regeneration |
| Extractor change | Positive/negative fixtures, offsets, sampled audit, scope guard |
| UI change | API contract, feature tests, browser/mobile check |
| Bulk operation | Preflight, lock, bounded scope, state/log review, recovery |
| Documentation change | Authority check, generated-source check, local-link validation |

## Modularization Task Decomposition

The manager should decompose large-file work by responsibility, not by arbitrary
line ranges. A valid task names one owner such as route registration, query
construction, response mapping, page rendering, source adaptation, merge
policy, extraction candidates, resolution, or persistence. It should identify
the old symbol path, the proposed new owner, compatibility period, and callers
to migrate.

For a multi-step refactor, create a chain of small tasks with separate
acceptance checks. The manager must not assign a route split and an extraction
rewrite under one ticket merely because both touch `routes.py` or `citations.py`.

## Evidence Requirements By State

`Mapped` requires an owner and dependency map. `In progress` requires a bounded
file/symbol scope. `Focused check passed` requires the named command output.
`Docs synchronized` requires affected canonical and Swimm documents updated.
`Complete` requires no unresolved acceptance item; a known unrelated failure
must be recorded separately rather than waived by prose.

## Escalation Rules

Pause and record a blocker when imports become cyclic, a response contract is
unclear, a migration cannot be safely reversed, offsets change unexpectedly,
or a bulk writer lacks a bounded recovery path. Escalate scope only by adding
a new acceptance check and updating the task record.

## Guardrails

- Never run competing bulk PostgreSQL writers.
- Never edit generated API, schema, script, or work-history documents manually.
- Never merge statute extraction into case-citation extraction.
- Never treat staged/discovered/activity data as an official captured judgment.
- Never use no-index headers as authentication.
- Never expand task scope without a new acceptance check.
- Never claim a suite or browser check passed unless it was actually run.

## Handoff States

`Proposed` -> `Mapped` -> `In progress` -> `Focused check passed` -> `Broader
check passed` -> `Docs synchronized` -> `Complete`. A task with a failing or
blocked check remains `Blocked` or `Needs repair`; it does not advance by prose.

## First Manager Sprint

Start by repairing the known test-collection issue, adding browser smoke
coverage for the active Data Explorer, defining data-quality measurements, and
protecting IRPA/IRPR extraction fixtures. Only then begin structural movement
of route, model, ingestion, or extraction modules.
