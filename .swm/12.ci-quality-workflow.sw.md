# Non-blocking CI Quality Workflow

## Purpose and boundaries

The quality workflow adds review signals without changing the required test
gate. Its executable owner is
[`.github/workflows/quality.yml`](../.github/workflows/quality.yml);
the existing required test workflow remains
[`.github/workflows/tests.yml`](../.github/workflows/tests.yml).

## Flow

1. A pull request or the weekly Sunday 00:00 UTC schedule starts two independent
   jobs. `workflow_dispatch` is also available for a manual baseline run.
2. Ruff checks the repository with `E` errors and `F401` unused-import rules.
   The audit checks `requirements.txt`, including resolved dependencies.
3. Each job records its pinned tool version, complete output, and exit code.
   Each uploads a separate artifact (`ruff-results` or `pip-audit-results`)
   even when tool installation or the check fails.
4. Both jobs are explicitly non-blocking. Review the uploaded results rather
   than interpreting a green workflow as an absence of findings.

## Invariants and failure modes

- Do not edit the existing test workflow as part of this quality signal.
- Do not silently drop or normalize non-zero tool exit statuses; status is part
  of each artifact.
- Ruff findings are an initial code-quality baseline, not a merge gate.
- pip-audit reports advisories for declared/resolved dependencies; it does not
  establish runtime reachability, production installation, or exploitability.
- An install/network failure is recorded separately from a clean scan.

The first observed results and interpretation are in
[`docs/reports/baseline-lint-and-audit.md`](../docs/reports/baseline-lint-and-audit.md).
The canonical workflow description is in
[`SYSTEM_REFERENCE.md`](../SYSTEM_REFERENCE.md). Workflow syntax and behavior
can be checked with YAML validation, the exact tool commands in the baseline
report, and `git diff --check`.

## Dependency update and SBOM workflow

Issue #171 adds a separate dependency-focused workflow at
[`.github/workflows/dependency-audit.yml`](../.github/workflows/dependency-audit.yml)
and weekly grouped update configuration at
[`.github/dependabot.yml`](../.github/dependabot.yml). The dedicated workflow
scans `requirements.txt` on requirement-file pull requests, every push to
`main`, and a weekly schedule; it keeps pip-audit and CycloneDX generation
non-blocking and uploads separate report/SBOM artifacts. CycloneDX tooling is
installed in that workflow only.

The canonical scope and review guidance, including report interpretation,
ownership, and the proposed patch SLA, is
[`docs/SECURITY_DEPENDENCIES.md`](../docs/SECURITY_DEPENDENCIES.md). This
workflow is additive; it does not replace or modify the existing test or
quality workflow. A green informational audit is not evidence of zero risk.

## Base and optional ML requirements

[`requirements.txt`](../requirements.txt) is the base application and CI
environment. It retains sentence-transformers because a CI test exercises
local semantic search. The spaCy package/model for automatic name detection
are lazy-loaded and listed separately in
[`requirements-ml.txt`](../requirements-ml.txt); the relevant test uses
`pytest.importorskip("spacy")` when they are absent. Install both manifests
only for automatic name detection; [`SETUP.md`](../SETUP.md) documents that
command. The test workflow and its explicit deselections are unchanged.
