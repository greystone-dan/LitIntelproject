# Frontend and UI Surfaces

## Architecture

The active formatted `/data-explorer` reader's paragraph-level **Similar
paragraphs** control calls `GET /cases/{case_id}/paragraphs/{n}/similar`.
`backend/paragraph_similarity.py` verifies stored exact canonical tag/citation
spans and numbered paragraph chunks, with indexed posting and row budgets.
Scoring is shared active V3 tags + twice shared cited case authorities; statutes
remain separate; distinct signals count once and ties use case ID then paragraph.
Bare-numbered SCC chunks require bounded actual canonical prefix context,
including the `Decision Content` marker and preceding sequence; insufficient
or ambiguous context is omitted rather than fabricated. Unresolved authority
discovery uses sorted-label ordered equality seeks sharing one postings budget
and one lookahead per signal, followed by deterministic candidate-ID merging.
Unvisited labels at budget exhaustion are reported as partial coverage. These
rules and context limits live in `backend/paragraph_similarity.py`; regressions
live in `tests/test_paragraph_similarity.py`.
The UI guards stale responses, explains bounded coverage and
opens returned case/paragraph deep links. Chunk indices and citation target
pinpoints are never treated as citing paragraph numbers. Migration
`0031_paragraph_similarity` mirrors its composite indexes in ORM metadata.

The active frontend is generated by Python page builders and route helpers,
with substantial HTML/CSS/JavaScript assembled around `backend/routes.py`.
This is a functional coupling point: a route can return HTTP 200 while its
browser script, tab state, or reader interaction is broken.
`tests/test_inline_js_syntax.py` renders the page modules and checks each inline
script with `node --check`, reporting the page module and script line; it skips
cleanly when Node.js is unavailable. This catches parse failures, not browser
runtime or interaction errors.

```mermaid
flowchart TD
	API[FastAPI JSON routes] --> Explorer[Data Explorer]
	Explorer --> Search[Case Search]
	Search --> Reader[Inline case reader]
	API --> Brief[Issue brief JSON / printable page]
	Brief --> Reader
	API --> Map[Citation Map]
	API --> Live[Live Analysis]
	API --> QA[Citation Pass]
	Reader --> Evidence[Backend-owned chunks, offsets, provenance]
```

## Active Surfaces

### Ephemeral proposition-to-authority research

The standalone Precedent Finder is owned by
`backend/precedent_finder.py` and `backend/pages/precedent_finder.py`, with
GET/POST orchestration in `backend/routes.py`. It reuses the existing V3
tagger and statute extractor, not embeddings or external analysis. Route
validation is deliberately manual and bounded: ordinary body-validation
errors can echo input, so this surface returns only fixed errors and no-store
responses. The page uses text-only DOM rendering, no browser storage, and
clears its proposition on exit. The application audit middleware records route
metadata rather than bodies; infrastructure logging is outside this guarantee.

Like paragraph similarity, discovery uses ordered equality posting seeks,
then bounded canonical source/target projections. Budgets charge fetched rows
before deduplication; caps and partial coverage are explained, not hidden.
Resolved case authorities are distinct from separately extracted statutes.
Source provenance/dataset exclusions keep noncanonical material out; legacy
canonical rows with missing source types remain eligible.

Ranking is lexicographic: distinct matching citing decisions, distinct matched
tags, authority date, then deterministic citation order. Tags describe the
matching **citing decisions** at decision level, not exact paragraph evidence
or citation treatment. The page prints the three numeric keys, court/date,
verified citing-source paragraph if available, and outcome counts with unclassified
records and an explicit distinct-matching-decision denominator. This is an
auditable navigation aid, not an assertion that the authority supports the
submitted proposition.

The finder reuses `backend/paragraph_similarity.py`'s bounded paragraph
location and citation-span verification, plus `backend/case_formatter.py`'s
actual block classification. Excerpts must contain an exact stored citation
occurrence to the returned authority in a uniquely located numbered source
paragraph. Chunk-local occurrence offsets are rebased by verified canonical
chunk location; short-form anchors remain document-relative. Target pinpoints
and chunk indices are not source paragraph numbers. Headers, unavailable or
invalid spans, ambiguous/repeated chunks and mixed structured chunks are
omitted, not replaced with authority text. Genuine paragraph continuations,
lists and quotes remain eligible.

Among verified candidates, choose by distinct matched tags on the **source
decision** descending, then source citation label, source ID, paragraph number
and citation row ID ascending. `excerpt_source` records these identifiers,
matched tags/count and the decision-level selection basis. The page explicitly
labels the citing source and links its paragraph in `/data-explorer`, separately
from the authority link. Verification cannot expand discovery IDs; paragraph
rows share a global budget, including rejected rows. Exact caps and projections
are owned by the finder and existing verification helpers, not browser offsets.

Exact budgets, projections, exclusions and response keys remain authoritative
in the service and route. `tests/test_precedent_finder.py` provides SQLite,
query-bound, duplicate, lexicographic, privacy/length and page contracts,
including source paragraphs versus target pinpoints, chunk-local/short-form
spans, missing/invalid/ambiguous evidence, mixed structured chunks and
deterministic excerpt selection.
See `SYSTEM_REFERENCE.md` for the public contract. Existing research routes,
source offsets, taxonomy rules and citation resolution are unchanged.
The combined architecture inventory in `docs/ARCHITECTURE.md` includes both
finder modules alongside the statute library and unit-search modules; these
research paths coexist without changing the finder's ephemeral input boundary.
The default-off enhanced-AI gate applies to optional embedding/generation paths,
not this deterministic finder. Keep both sets of route imports when integrating
reader markup, alert digests, and versioned prompts; finder privacy and bounded
evidence tests remain independent contracts.

### Two-decision comparison

The pre-existing `/case-compare` search-first page and
`GET /cases/compare?a=<case_id>&b=<case_id>` JSON endpoint remain separate and
available. Issue #231 adds `/compare?a=<case_id-or-citation>&b=...` and its
`GET /api/compare?a=...&b=...` JSON contract. Both IDs and stored formal
citations are accepted by the new routes. The page renderer keeps its form
action explicit: the legacy page submits to `/case-compare`, while the new page
submits to `/compare`. `backend/pages/case_compare.py` renders responsive decision cards,
separate tag/statute/authority lists, shared/unique badges, outcome provenance,
stored authority pinpoints, and whether either decision cites the other. The
page works with ordinary query forms and manual IDs/citations without
JavaScript; optional pickers reuse `/analytics/search/cases`. Search requests
are debounced, abortable and sequence guarded; labels are inserted with
`textContent`, and stored page values are HTML escaped.

`backend/case_compare.py` resolves IDs or citations against the existing local
case-resolution index, then adds stored cross-citation and pinpoint context to
the comparison projection. It rejects inputs over 512 characters before
trimming, numeric conversion, or citation normalization; `/api/compare` also
declares that query bound. `Citation.target_paragraph` means the cited
decision's paragraph; source occurrence paragraphs are read from the citing
decision's source chunk. A cites B/B cites A is shown only for an exact stored
`Citation.target_case_id` match to the other compared case. It does not make
external lookups, extract new citations, or write data.
`backend/case_comparison.py` owns the
stored-evidence signal projection. It deduplicates active taxonomy
category/value pairs, resolved authority target IDs and unresolved stored
neutral/reporter identifiers. Stored short-form anchors supply their unresolved
identity; explicit trailing paragraph/page pinpoints are excluded from fallback
identity labels. No unresolved/resolved or neutral/reporter equivalence is
inferred. Statute instrument/provision identities use the existing provision
normalizer, retaining ranges and lists (otherwise normalized labels). These
layers stay separate. Latest outcome assignment selection matches the reader's
updated-time/ID order; only missing assignments fall back to explicitly
attributed reader metadata. Unclassified outcomes and raw labels remain visible.
Facts and assignment evidence are displayed as stored and unverified.

`backend/routes.py` keeps `/cases/compare` and `/case-compare` compatibility,
and adds `/api/compare` plus `/compare`. Unknown inputs receive a clear 404;
the HTML page explains the miss and the JSON response identifies unknown
inputs. Comparing a decision with itself is politely rejected. The Data
Explorer reader adds a no-JavaScript “Compare with…” link prefilled with its
case ID. The earlier walkthrough omitted a header shortcut to keep the old
reader scope contained; issue #231 explicitly requests this additive link, so it
is now a plain prefill link rather than new reader controls or behavior. Issue
#112's keyboard, print, and other reader features remain intact. The
comparison does not change reader offsets, startup, schema or canonical rows.

## Evidence Rendering Rules

The backend owns citation/statute/metadata offsets. The browser may render
highlights and linked authority context but must not infer substitute spans,
reparse the decision, or silently change evidence. Source HTML is presentation;
chunk text and persisted offsets remain the evidence location of record.

Chunk and full-text rendering use different overlap precedence: chunk mode
renders citation spans before applying tag marks, while full text resolves the
combined range set. Overlapping evidence may therefore produce different DOM
mark counts; browser smoke validation checks that both modes retain visible
tag evidence rather than requiring identical counts.

Chunk mode keeps each stored chunk as a structural article for evidence and
ordering, but presents the articles as a continuous judgment with compact body
padding and subtle separators. Visible chunk labels, ordinal fallbacks,
chunk-set names, and character counts are suppressed. Citation and statute
marks inherit the surrounding judgment font size and line height; their color,
link behavior, evidence attributes, and backend-owned offsets remain unchanged.

## UI Refactoring Rules

Separate page construction, API payload assembly, and browser behavior only
after contract tests identify their dependencies. Preserve empty states,
long-text scrolling, linked-authority navigation, independent panes, hover
previews, and responsive stacking. Do not duplicate a legacy reader to fix the
active one; `/data-explorer` is the canonical research workflow.

## Page And Browser Responsibilities

Page builders should produce stable page shells and predictable element names;
browser code should manage interaction state and call documented API routes;
the API should provide complete evidence payloads. A browser highlight is a
rendering of an offset supplied by the backend, not an extraction result.

The active reader depends on case identity, source/provenance, chunks, citation
rows, statute rows, tags, metrics, and linked authority context. Empty,
unresolved, incomplete, and unavailable states need distinct rendering. Long
decisions require stable scrolling and independently usable context panes.

## Case Reader Evidence Layers

The inline reader keeps three evidence layers visually distinct:

- **Green:** legal tags from stored or inferred taxonomy records. The Tags panel
	groups entries by unique category/value and expands to show each occurrence,
	evidence excerpt, source, score, taxonomy version, and backend offset when
	available.
- **Purple:** statutes and regulations from the independent statute-reference
	layer, including IRPA/IRPR provisions.
- **Yellow:** case-to-case citation occurrences and linked authorities.

The color treatment is a rendering aid only. Backend-owned offsets, provenance,
and layer separation remain authoritative. A missing highlight or occurrence
does not justify inventing a browser-side span.

### Statute consideration

The Statute Library links to `/statute-consideration`, where a researcher can
enter a stored Act name/key and base section. The read-only endpoint
`GET /api/statutes/{act}/{section}/consideration` groups persisted statute-reference occurrences
by distinct decision, and separately reports the occurrence total. Court, year,
and outcome counts also use distinct decisions; every outcome split includes
`unclassified` and states its all-decision denominator. Displayed cases include the statute
version selected for their decision date. Case rows rank by
reference count within the decision and then recency, with at most 50 rows per
page; each row opens the existing case reader. The page explicitly labels these
as descriptive statistics, not legal-effect or causal findings. Unknown Acts
and sections produce a 404 with an input hint. Implementation lives in
[`backend/statute_consideration.py`](../backend/statute_consideration.py), with
fixture coverage in `tests/test_statute_consideration.py`.

The active reader may also show an additive overruling-risk banner populated by
`GET /api/overruling-risk/{case_id}`. It appears only when a direct seed match or
a stored resolved citation to a seeded authority is returned; an unavailable
lookup is not treated as a negative legal finding. The banner shows the
development, source, rationale, decision/event dates, notice, and how the flag
was assigned. Its wording says the case **may be affected**. A stored citation
is a traceable reference, not proof of reliance or legal effect; the indicator
is not a treatment determination. Every entry and flag says “seed list, needs
lawyer review.” If the requested case is the listed development authority, the
banner identifies it as the source of the development and says other cases may
be affected instead of implying that it is affected by itself. Seed extension
and test guidance is in
[`docs/reports/overruling-risk.md`](../docs/reports/overruling-risk.md).
The warning renderer is isolated in
[`backend/pages/overruling_risk_reader.js`](../backend/pages/overruling_risk_reader.js);
the shell exposes its accessible banner region in
[`backend/pages/data_explorer.py`](../backend/pages/data_explorer.py).

Browser validation on a Vavilov search result confirmed the reader displays all
three layers together: green tag highlights, purple statute highlights, and
yellow citation highlights. The Tags panel rendered 19 unique tags across 111
stored or inferred occurrences, while the Citations and Acts / Regs panels
continued to show grouped citation occurrences and persisted statute rows.

The full-text reader also shades a numbered paragraph when stored incoming
case-citation evidence has a pinpoint for it, with a tooltip such as
“Cited by 12 cases”. The backend counts distinct citing cases and maps only the
existing pinpoint to a formatter-produced paragraph; this display cue does not
change source citation offsets or create browser-side spans. Missing or
unmatched pinpoints leave paragraphs in their normal style. See
[`backend/reader_service.py`](../backend/reader_service.py) and
[`backend/case_formatter.py`](../backend/case_formatter.py).

### Keyboard navigation and print

The inline reader supports `j`/`n` for the next formatted paragraph and `k`/`p`
for the previous one. Navigation focuses and visibly marks the current paragraph;
it switches to formatted text when paragraph anchors are not present in the
current reader mode. The `?` control or key opens the shortcut list, and Escape
closes it. Keyboard actions are ignored while a text-entry or editable control
has focus. Printing keeps the case title, citation, and paragraph numbers while
hiding reader navigation, side panels, and controls; paragraph blocks are kept
together across pages where possible. These are presentation behaviors only:
paragraph identity and evidence offsets continue to come from the backend
formatter. See [`backend/pages/data_explorer.py`](../backend/pages/data_explorer.py)
and [`docs/RESEARCH_UI_GUIDE.md`](../docs/RESEARCH_UI_GUIDE.md).

### Extracted summary above the source text

Issue #152 adds the read-only `GET /api/cases/{case_id}/summary` projection in
[`backend/case_summary.py`](../backend/case_summary.py), with fixtures in
[`tests/test_case_summary.py`](../tests/test_case_summary.py). Minimal router
inclusion in [`backend/routes.py`](../backend/routes.py) registers it through
the existing application router. No startup or database lifecycle changes are
required. This projection reads stored identity fields and the latest
outcome/source (unclassified/unknown when absent), without classification.
Unlike the existing verified-facts card below, stored metadata/outcome labels
remain visible even when no verified source paragraph is available.

The separate renderer
[`backend/pages/case_quick_summary.py`](../backend/pages/case_quick_summary.py)
is injected last into the active Data Explorer page. Its default-open native
disclosure is mounted first in formatted decision text, preserving both
existing summary controls. Closing/reopening resets disclosure state; mode
changes preserve it. Aborted, unavailable, mismatched and stale case responses
cannot replace another case's card or disrupt its reader.
Late script installation also adopts initial `case_id` deep links, whether
their existing reader request is still pending or has already completed.

Extraction rules are deliberately conservative: exact stored disposition
offsets must fit one numbered formatter paragraph (including continuation
blocks), whose complete source slice is displayed verbatim. Issue openings or
explicit issue/review headings permit one or two complete verbatim sentences;
the first issue candidate is preferred over review. Unknown abbreviations,
quotes and unfinished tails cause omission. Openings/headings currently
support explicit English forms only. Five distinct active-taxonomy tags
at most require exact paragraph evidence and finite scores. Five statute keys
at most count stored statute/instrument occurrences; case citations remain
separate. Chunk-relative statute references retain counts but omit evidence
links, because this projection intentionally does not retrieve/rebase chunks.
Statutes sort by descending count then key; tags by descending score then
category/value, with stable evidence tie-breaks.
The renderer omits unavailable identity rows, disposition/issue sections and
empty statutes/tags without placeholder prose. Outcome/source always remain
visible (unclassified/unknown when absent). Statute counts need no excerpt;
tags failing browser evidence verification are omitted entirely.

Every displayed value is escaped. Browser verification uses `Array.from` for
Python Unicode code-point spans, never UTF-16 string slicing or invented source
offsets. Links use backend block starts plus paragraph identity, so duplicate
paragraph numbers focus the correct block. Fixture coverage in
[`tests/test_case_quick_summary_ui.py`](../tests/test_case_quick_summary_ui.py)
includes Node stale-response/escaping checks and offline Chrome disclosure,
focus, Unicode, existing-card retention and narrow-screen checks. Focused
command: `python -m pytest tests/test_case_summary.py tests/test_case_quick_summary_ui.py -q`.
Live PostgreSQL, deployment and full search workflow are not part of those
fixtures; stored counts do not imply corpus completeness.

The active reader adds an always-visible, compact **Extracted case summary**
only when verified source facts exist. This is distinct from the optional technical
**Show case summary** control. The reader service selects the latest stored
`CaseOutcome` and adds a dedicated `extracted_summary` evidence projection
alongside the existing extracted metadata;
it does not invoke the outcome classifier in
[`backend/metadata_outcomes.py`](../backend/metadata_outcomes.py).
The page renders only this verified projection, never raw court/date/judge/tag
fallbacks. Every fact has an individual link. Court and date must match explicit
source-header forms; judge also requires existing extraction evidence and a
judge-labelled header match. Header links are labelled **Source header** because
these formatter blocks need not be numbered. Unsupported formats/abbreviations
are omitted, not searched for in unrelated body paragraphs.
Judge headers accept only prefixes already supported by the judge normalizer in
[`fc_ingest/document_scraper.py`](../fc_ingest/document_scraper.py), such as
`The Honourable` before stored `Paul U.C. Rouleau`. The exact stored name remains
the captured evidence span; prefixes do not change its offsets or formatter
source-link identity. Arbitrary prefix text is not accepted.
At most three distinct stored tags with exact document evidence offsets inside
numbered paragraphs are selected by score with category/value tie-breaks.
Inferred tags and stale/partial offsets are excluded. These are stored signals,
not newly generated labels or prose.

A disposition quotation requires the stored evidence offsets to reproduce
the stored evidence exactly in canonical full text and fall within a numbered
formatter paragraph (including its continuation blocks). The quotation is a
verbatim source slice, escaped for display. Unverified, unnumbered, or
cross-paragraph evidence is omitted rather than assigned a guessed location.
Outcome and its displayed stored extraction source reuse this same verified
paragraph link; neither appears if evidence is invalid. A quotation can remain
without an outcome label. Source links switch to formatted mode and focus the
backend formatter block start with its paragraph identity, avoiding ambiguity
from repeated paragraph numbers. The browser only copies supplied block starts
into anchors; it does not calculate or search for replacement evidence offsets.
The summary is remounted above source text when reader modes change.

The separate issue #232 **Quick summary · selected passages** card is served by
`GET /api/cases/{case_id}/summary-card` and implemented in
[`backend/case_summary_card.py`](../backend/case_summary_card.py), with its
conditional formatted-reader controller in
[`backend/pages/case_summary_card.py`](../backend/pages/case_summary_card.py).
It does not replace the existing `/summary` projection or Extracted case
summary. It returns only stored citation/court/date, a judge accepted by the
reader's labelled-header evidence rules, the latest stored outcome with source
and determination status, separate statute occurrence counts and active-tag
scores/provenance, and up to three exact numbered passages.

Passages are selected by stored disposition evidence (or a paragraph beneath
an explicit Conclusion/Disposition heading), highest incoming resolved
pinpoint occurrence count from decisions dated later than the subject case,
and an explicit standard-of-review statement/heading. Each quote carries its
formatter paragraph number, exact full paragraph text, backend offsets, and
the rule which chose it. Pinpoint ties use ascending paragraph number; a
duplicate number that cannot identify one exact formatted block is omitted.
The query counts only stored citation rows with resolved target and explicit
target paragraph and later source-case date; it makes no claim of exhaustive
coverage.

The card is collapsed by default and is not mounted for an empty/unusable
response. Its fixed notice says **“Selected passages, not a summary written by
AI”**. Long quotes are shortened only at a safe sentence boundary, receive an
ellipsis, and link to the complete reader paragraph. Display values are
escaped; the browser verifies the exact full-text code-point span against the
reader's formatter blocks before navigating to the supplied backend block start.
Missing source fields, including an absent outcome source, are omitted rather
than labelled unknown. This route is read-only: it does not call a classifier,
generate prose, write a summary, or modify citations, tags, statutes, or offsets.

Implementation remains in
[`backend/reader_service.py`](../backend/reader_service.py) and
[`backend/pages/data_explorer.py`](../backend/pages/data_explorer.py), with the
additive response contract in [`backend/models.py`](../backend/models.py).
Focused projection/serialization coverage is in
[`tests/test_reader_service.py`](../tests/test_reader_service.py), with rendering,
escaping, tag limits, and mode-remount checks in
[`tests/test_feature_tabs.py`](../tests/test_feature_tabs.py). Run
`python -m pytest -q tests/test_reader_service.py tests/test_feature_tabs.py`.
Browser acceptance should also open cases with and without stored outcomes,
compare the quotation to source text, follow the paragraph link from chunk
mode, and check sparse/mobile rendering. Source records and formatter offsets
must remain unchanged.
The optional `test_extracted_summary_browser_source_links` in the UI tests
uses locally available Playwright/Chromium, backend-projected synthetic stored
text, and the actual renderer/click handler. It checks desktop/mobile focus
for every item from chunk mode, missing/invalid outcomes, and empty summaries.
It does not query a live database or verify an end-to-end search deployment;
without existing browser tooling it is explicitly skipped, not installed.

The source pane includes a persistent legend for the three colors. The Tags
panel reports unique groups separately from total occurrence rows, preserving
sparse cases as returned by the backend rather than inventing additional tag
instances.

The source pane also provides a `Show evidence details` control. When enabled,
selecting an existing citation, statute, or tag highlight opens a compact
inspector using the backend-provided authority and target attributes. This is a
rendering aid over existing evidence, not a browser-side offset or resolution
system.

Reader-inferred tags use one canonical text representation when available and
retain repeated matches up to a bounded per-tag limit. In the OU v. Canada
audit, 18 standalone `ID` tokens produced 27 `forum: id` matches because the
same rule also recognizes the full phrase `Immigration Division`; the UI shows
all of those evidence rows under one unique tag group.

Source HTML normalization is being introduced as a separate pipeline foundation
in `backend/document_structure.py`. It derives sanitized display HTML, headings,
paragraphs, list items, table rows, and canonical text ranges without mutating
the acquired source. Chunking and evidence integration remain a later stage
until the plain-text-to-source mapping is carried through citations, statutes,
and tags.

The source-preserving mapper records HTML block paths and canonical text ranges
for future pretty rendering. It does not yet replace the reader's evidence text
or chunk boundaries; only mapped, confidence-checked ranges may do that in a
later integration slice.

The three reader chunk layers are now populated by the operational writer. Cases
with confidently mapped HTML receive HTML-informed section and paragraph
boundaries; text-only cases use the existing deterministic fallback. Both paths
preserve canonical text for citation, statute, and tag evidence.

The same structural document contract must serve the live user-document path:
inventory HTML and live DOCX/PDF inputs may use different adapters, but both
should emit headings, paragraphs, larger sections, canonical text ranges, and
formatting metadata before citations, statutes, tags, or reader highlights are
produced. Live analysis remains ephemeral and separate from canonical inventory
writes.

The reader can select the paragraph layer for precise evidence while retaining
section and full-case layers for larger context. The operational chunk writer
creates all three named layers; paragraph and section rows carry readable labels
and paragraph metadata where the source text supports them.

The Legal Themes & Statutes tab calls `/analytics/themes` and
`/analytics/statute-tag-matrix`. Its Precedents reader panel calls the bounded
`/analytics/cases/{case_id}/thematic-cluster` route. These displays remain
derived research signals; browser code does not create offsets or replace
persisted citation/statute provenance.

## Modularization Direction

Move one page family at a time: page shell, styles, browser behavior, route
payload assembly, then query helpers. Keep compatibility routes and payload
field names until feature tests and a browser smoke check cover the new owner.
Do not move the legacy `/case-reader` into the active reader module as a shortcut.

## UI Risk Inventory

### Panel-local outage recovery

The active page includes the shared inline builder from
[`backend/degraded_mode.py`](../backend/degraded_mode.py) once. Its `fetchPanel`
checks HTTP status and JSON parsing, supplies an `aria-live="polite"` loading
state, and installs a plain-language failure plus Retry. The renderer callback
owns both first success and retry success, including event binding.
[`backend/pages/data_explorer.py`](../backend/pages/data_explorer.py) queues
changed selections per container and guards stale reader tabs, searches and
judge profiles. Shared-response panels reuse their original response rather
than add requests. FC dashboard, judge and counsel renderers are independent
in [`backend/pages/fc_analytics.py`](../backend/pages/fc_analytics.py).
Neither failed requests nor later catches may replace sibling panels or the
Retry controls. Source offsets and successful endpoint shapes remain owned by
the existing backend.

`node tests/test_panel_helpers.js` exercises actual helpers and owner callbacks
with offline fixtures. `node tests/test_panel_browser.js` uses installed
Chromium against a temporary, fixture-only page to check isolation, disabled
retry, loading accessibility and the actual Case Search renderer. These do not
replace the Python HTTP/feature contracts or a full application browser check.

The 2026-10-04 offline acceptance passed 240 outage/readiness/feature/paragraph
tests (one optional Playwright skip), including both Node checks through the
existing pytest infrastructure. The paragraph-similarity browser fixture now
loads the real shared helper/selection queue and verifies successful Retry as
well as stale-result rejection. Full pytest passed 1,919 tests with exactly
the three CI deselections, five skips and one expected failure. See the
[canonical validation checkpoint](../SYSTEM_REFERENCE.md#runtime-components)
for environment and live-system limitations.

The dangerous regressions are HTTP-success/JavaScript-failure, stale tab state,
missing mobile stacking, clipped long text, duplicate event handlers, incorrect
highlight spans, and reader links that lose source context. These require
browser evidence; Python compilation alone cannot disprove them.
