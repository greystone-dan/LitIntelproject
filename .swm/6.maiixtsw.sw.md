# Frontend and UI Surfaces

## Architecture

The active formatted `/data-explorer` reader's paragraph-level **Similar
paragraphs** control calls `GET /cases/{case_id}/paragraphs/{n}/similar`.
`backend/paragraph_similarity.py` verifies stored exact canonical tag/citation
spans and numbered paragraph chunks, with indexed posting and row budgets.
Scoring is shared active V3 tags + twice shared cited case authorities; statutes
remain separate; distinct signals count once and ties use case ID then paragraph.
Bare-numbered SCC chunks require bounded actual canonical prefix context,
including the `Decision Content` marker and preceding sequence; insufficient
or ambiguous context is omitted rather than fabricated. Unresolved authority
discovery uses sorted-label ordered equality seeks sharing one postings budget
and one lookahead per signal, followed by deterministic candidate-ID merging.
Unvisited labels at budget exhaustion are reported as partial coverage. These
rules and context limits live in `backend/paragraph_similarity.py`; regressions
live in `tests/test_paragraph_similarity.py`.
The UI guards stale responses, explains bounded coverage and
opens returned case/paragraph deep links. Chunk indices and citation target
pinpoints are never treated as citing paragraph numbers. Migration
`0031_paragraph_similarity` mirrors its composite indexes in ORM metadata.

The active frontend is generated by Python page builders and route helpers,
with substantial HTML/CSS/JavaScript assembled around `backend/routes.py`.
This is a functional coupling point: a route can return HTTP 200 while its
browser script, tab state, or reader interaction is broken.

```mermaid
flowchart TD
	API[FastAPI JSON routes] --> Explorer[Data Explorer]
	Explorer --> Search[Case Search]
	Search --> Reader[Inline case reader]
	API --> Brief[Issue brief JSON / printable page]
	Brief --> Reader
	API --> Map[Citation Map]
	API --> Live[Live Analysis]
	API --> QA[Citation Pass]
	Reader --> Evidence[Backend-owned chunks, offsets, provenance]
```

## Evidence Rendering Rules

The backend owns citation/statute/metadata offsets. The browser may render
highlights and linked authority context but must not infer substitute spans,
reparse the decision, or silently change evidence. Source HTML is presentation;
chunk text and persisted offsets remain the evidence location of record.

Chunk and full-text rendering use different overlap precedence: chunk mode
renders citation spans before applying tag marks, while full text resolves the
combined range set. Overlapping evidence may therefore produce different DOM
mark counts; browser smoke validation checks that both modes retain visible
tag evidence rather than requiring identical counts.

Chunk mode keeps each stored chunk as a structural article for evidence and
ordering, but presents the articles as a continuous judgment with compact body
padding and subtle separators. Visible chunk labels, ordinal fallbacks,
chunk-set names, and character counts are suppressed. Citation and statute
marks inherit the surrounding judgment font size and line height; their color,
link behavior, evidence attributes, and backend-owned offsets remain unchanged.

### Most cited paragraphs

`backend/pages/data_explorer.py` owns the native, initially collapsed
`readerMostCited` disclosure. It ranks positive `format_blocks` paragraph
integer counts by descending count, then ascending numeric paragraph number,
keeping the earliest block for each paragraph number before ranking at most
five. `backend/reader_service.py` already deduplicates other
citing case IDs for paragraph shading; `backend/case_formatter.py` attaches
those counts and canonical code-point spans. The panel consumes that payload
without another query or new API fields.

Excerpts slice the stored full text by those code-point spans and are escaped.
Jump links prevent default fragment navigation and force normalized formatting,
then scroll (respecting reduced motion) and visibly focus the formatter's
`decision-source-<block.start>` anchor inside `decisionBody`. The panel and
extracted case summary share these backend-block anchors; the panel's mode
wrapper must not overwrite their IDs with paragraph-number IDs. Linked context
is never selected as a jump target. Open/load failure/close wrappers clear stale disclosure
content. `tests/test_feature_tabs.py::test_reader_most_cited_paragraphs_ranking_jumps_and_reset`
executes the controller with Node, including ties, empty state, Unicode,
escaping, source-only anchors, mode changes, and resets. Usage is documented
in `docs/RESEARCH_UI_GUIDE.md`; count semantics remain in `SYSTEM_REFERENCE.md`.

## UI Refactoring Rules

Separate page construction, API payload assembly, and browser behavior only
after contract tests identify their dependencies. Preserve empty states,
long-text scrolling, linked-authority navigation, independent panes, hover
previews, and responsive stacking. Do not duplicate a legacy reader to fix the
active one; `/data-explorer` is the canonical research workflow.

## Page And Browser Responsibilities

Page builders should produce stable page shells and predictable element names;
browser code should manage interaction state and call documented API routes;
the API should provide complete evidence payloads. A browser highlight is a
rendering of an offset supplied by the backend, not an extraction result.

The active reader depends on case identity, source/provenance, chunks, citation
rows, statute rows, tags, metrics, and linked authority context. Empty,
unresolved, incomplete, and unavailable states need distinct rendering. Long
decisions require stable scrolling and independently usable context panes.

## Case Reader Evidence Layers

The inline reader keeps three evidence layers visually distinct:

- **Green:** legal tags from stored or inferred taxonomy records. The Tags panel
	groups entries by unique category/value and expands to show each occurrence,
	evidence excerpt, source, score, taxonomy version, and backend offset when
	available.
- **Purple:** statutes and regulations from the independent statute-reference
	layer, including IRPA/IRPR provisions.
- **Yellow:** case-to-case citation occurrences and linked authorities.

The color treatment is a rendering aid only. Backend-owned offsets, provenance,
and layer separation remain authoritative. A missing highlight or occurrence
does not justify inventing a browser-side span.

Browser validation on a Vavilov search result confirmed the reader displays all
three layers together: green tag highlights, purple statute highlights, and
yellow citation highlights. The Tags panel rendered 19 unique tags across 111
stored or inferred occurrences, while the Citations and Acts / Regs panels
continued to show grouped citation occurrences and persisted statute rows.

The full-text reader also shades a numbered paragraph when stored incoming
case-citation evidence has a pinpoint for it, with a tooltip such as
“Cited by 12 cases”. The backend counts distinct citing cases and maps only the
existing pinpoint to a formatter-produced paragraph; this display cue does not
change source citation offsets or create browser-side spans. Missing or
unmatched pinpoints leave paragraphs in their normal style. See
[`backend/reader_service.py`](../backend/reader_service.py) and
[`backend/case_formatter.py`](../backend/case_formatter.py).

### Extracted summary above the source text

The active reader adds an always-visible, compact **Extracted case summary**
only when verified source facts exist. This is distinct from the optional technical
**Show case summary** control. The reader service selects the latest stored
`CaseOutcome` and adds a dedicated `extracted_summary` evidence projection
alongside the existing extracted metadata;
it does not invoke the outcome classifier in
[`backend/metadata_outcomes.py`](../backend/metadata_outcomes.py).
The page renders only this verified projection, never raw court/date/judge/tag
fallbacks. Every fact has an individual link. Court and date must match explicit
source-header forms; judge also requires existing extraction evidence and a
judge-labelled header match. Header links are labelled **Source header** because
these formatter blocks need not be numbered. Unsupported formats/abbreviations
are omitted, not searched for in unrelated body paragraphs.
Judge headers accept only prefixes already supported by the judge normalizer in
[`fc_ingest/document_scraper.py`](../fc_ingest/document_scraper.py), such as
`The Honourable` before stored `Paul U.C. Rouleau`. The exact stored name remains
the captured evidence span; prefixes do not change its offsets or formatter
source-link identity. Arbitrary prefix text is not accepted.
At most three distinct stored tags with exact document evidence offsets inside
numbered paragraphs are selected by score with category/value tie-breaks.
Inferred tags and stale/partial offsets are excluded. These are stored signals,
not newly generated labels or prose.

A disposition quotation requires the stored evidence offsets to reproduce
the stored evidence exactly in canonical full text and fall within a numbered
formatter paragraph (including its continuation blocks). The quotation is a
verbatim source slice, escaped for display. Unverified, unnumbered, or
cross-paragraph evidence is omitted rather than assigned a guessed location.
Outcome and its displayed stored extraction source reuse this same verified
paragraph link; neither appears if evidence is invalid. A quotation can remain
without an outcome label. Source links switch to formatted mode and focus the
backend formatter block start with its paragraph identity, avoiding ambiguity
from repeated paragraph numbers. The browser only copies supplied block starts
into anchors; it does not calculate or search for replacement evidence offsets.
The summary is remounted above source text when reader modes change.

Implementation remains in
[`backend/reader_service.py`](../backend/reader_service.py) and
[`backend/pages/data_explorer.py`](../backend/pages/data_explorer.py), with the
additive response contract in [`backend/models.py`](../backend/models.py).
Focused projection/serialization coverage is in
[`tests/test_reader_service.py`](../tests/test_reader_service.py), with rendering,
escaping, tag limits, and mode-remount checks in
[`tests/test_feature_tabs.py`](../tests/test_feature_tabs.py). Run
`python -m pytest -q tests/test_reader_service.py tests/test_feature_tabs.py`.
Browser acceptance should also open cases with and without stored outcomes,
compare the quotation to source text, follow the paragraph link from chunk
mode, and check sparse/mobile rendering. Source records and formatter offsets
must remain unchanged.
The optional `test_extracted_summary_browser_source_links` in the UI tests
uses locally available Playwright/Chromium, backend-projected synthetic stored
text, and the actual renderer/click handler. It checks desktop/mobile focus
for every item from chunk mode, missing/invalid outcomes, and empty summaries.
It does not query a live database or verify an end-to-end search deployment;

The source pane includes a persistent legend for the three colors. The Tags
panel reports unique groups separately from total occurrence rows, preserving
sparse cases as returned by the backend rather than inventing additional tag
instances.

The source pane also provides a `Show evidence details` control. When enabled,
selecting an existing citation, statute, or tag highlight opens a compact
inspector using the backend-provided authority and target attributes. This is a
rendering aid over existing evidence, not a browser-side offset or resolution
system.

Reader-inferred tags use one canonical text representation when available and
retain repeated matches up to a bounded per-tag limit. In the OU v. Canada
audit, 18 standalone `ID` tokens produced 27 `forum: id` matches because the
same rule also recognizes the full phrase `Immigration Division`; the UI shows
all of those evidence rows under one unique tag group.

Source HTML normalization is being introduced as a separate pipeline foundation
in `backend/document_structure.py`. It derives sanitized display HTML, headings,
paragraphs, list items, table rows, and canonical text ranges without mutating
the acquired source. Chunking and evidence integration remain a later stage
until the plain-text-to-source mapping is carried through citations, statutes,
and tags.

The source-preserving mapper records HTML block paths and canonical text ranges
for future pretty rendering. It does not yet replace the reader's evidence text
or chunk boundaries; only mapped, confidence-checked ranges may do that in a
later integration slice.

The three reader chunk layers are now populated by the operational writer. Cases
with confidently mapped HTML receive HTML-informed section and paragraph
boundaries; text-only cases use the existing deterministic fallback. Both paths
preserve canonical text for citation, statute, and tag evidence.

The same structural document contract must serve the live user-document path:
inventory HTML and live DOCX/PDF inputs may use different adapters, but both
should emit headings, paragraphs, larger sections, canonical text ranges, and
formatting metadata before citations, statutes, tags, or reader highlights are
produced. Live analysis remains ephemeral and separate from canonical inventory
writes.

The reader can select the paragraph layer for precise evidence while retaining
section and full-case layers for larger context. The operational chunk writer
creates all three named layers; paragraph and section rows carry readable labels
and paragraph metadata where the source text supports them.

The Legal Themes & Statutes tab calls `/analytics/themes` and
`/analytics/statute-tag-matrix`. Its Precedents reader panel calls the bounded
`/analytics/cases/{case_id}/thematic-cluster` route. These displays remain
derived research signals; browser code does not create offsets or replace
persisted citation/statute provenance.

## Modularization Direction

Move one page family at a time: page shell, styles, browser behavior, route
payload assembly, then query helpers. Keep compatibility routes and payload
field names until feature tests and a browser smoke check cover the new owner.
Do not move the legacy `/case-reader` into the active reader module as a shortcut.

## UI Risk Inventory

The dangerous regressions are HTTP-success/JavaScript-failure, stale tab state,
missing mobile stacking, clipped long text, duplicate event handlers, incorrect
highlight spans, and reader links that lose source context. These require
browser evidence; Python compilation alone cannot disprove them.
