# Testing and Quality Gates

## Test Pyramid

The suite combines deterministic unit tests, route/contract tests, source
pipeline tests, operational tests, and sampled real-corpus audits. Mocked tests
should remain fast and safe; live network, hosted model, and destructive corpus
runs are explicit operational checks rather than normal regression tests.

| Change surface | Minimum evidence |
| --- | --- |
| Citation/statute rule | Focused citation tests, positive/negative fixture, exact offsets |
| API/search | Relevant API tests, invalid/bounded cases, response contract |
| UI/reader | Feature-tab tests, compile check, browser interaction check |
| Metadata | Metadata tests and relevant API payload checks |
| Ingestion | Merge tests, importer tests, bounded dry-run |
| Schema/model | Migration inspection, schema generation, affected route tests |
| Operations | `--help`, orchestration tests, preflight or dry-run |

## Quality Gates

Required evidence is: no new diagnostics, focused tests green, generated docs
refreshed when sources change, and honest reporting of broader failures. The
full suite must not be called green while collection errors or stale contract
failures remain. Current known gaps include browser end-to-end coverage, live
PostgreSQL performance baselines, continuous real-corpus extraction precision,
and human-adjudicated classifier coverage.

## Data Quality

The next high-value gate should measure orphan links, malformed citations,
duplicate edges, null metadata, invalid offsets, unresolved-reference rates,
and source/provenance completeness. Counts must distinguish occurrences from
unique entities and extraction coverage from extraction cleanliness.

## Evidence By Change Type

| Change | Falsifiable check | Additional evidence |
| --- | --- | --- |
| pure helper/module move | old and new focused tests | import/caller check |
| extraction rule | positive, negative, exact span | bounded corpus audit |
| route contract | valid, invalid, empty, bounded requests | generated API check |
| reader/UI | feature test and compile | browser/mobile interaction |
| schema | migration inspection and model import | fresh/existing DB check |
| bulk writer | preflight/dry-run | bounded report and recovery path |

## Characterization Before Refactoring

Before moving a large module, record the current public symbols, imports,
database writes, route paths, response keys, side effects, and known failures.
This baseline is especially important for `routes.py`, `database.py`, and
`citations.py`, where a successful import can coexist with a behavioral change.

## Test Organization Direction

Keep fast unit fixtures close to rule behavior, contract tests at API
boundaries, integration tests for database relationships, and bounded audits
for corpus behavior. Avoid making every test depend on PostgreSQL or live
network access; reserve those dependencies for explicit integration checks.

## Release Sequence

1. Run the focused tests for the changed owner surface.
2. Compile touched Python modules and inspect diagnostics.
3. Run route/UI or source-pipeline checks as applicable.
4. Refresh generated API/schema/script docs.
5. Run the broader suite and record failures with owner and cause.
6. Run bounded browser/API, performance, or data-quality checks required by scope.
7. Review `git diff --check` and update the canonical docs.
