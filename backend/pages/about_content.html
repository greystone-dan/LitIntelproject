iLit: where the project stands

iLit is a litigation intelligence tool for immigration law that I have been building independently. It reads every Federal Court immigration file and decision, connects them, and answers the questions a litigation analyst is asked every week, with the source behind every answer. This is where it is today, and where it could go next.

In short: this is not a request to adopt anything or start a pilot. The project runs on public data, outside government, and moves quickly because of it. The last section sets out an unofficial idea of what modest funding would speed up, in three sizes.

The big picture

How it works

iLit uses public information only. It collects it, keeps the original untouched, reads it into facts, and connects the pieces.

What makes it unique · 1

It tracks every Federal Court file, not just the ones with decisions

Today, checking what has happened on a Federal Court immigration file means looking it up on the court’s website by hand, one case at a time. iLit already holds the docket history of every immigration file ever filed, 316,940 of them with 3.6 million entries, available instantly. It is designed to be refreshed so it stays accurate.

Why that matters: statistics can cover every case ever filed, not only the files JRU received. Most immigration files never produce a published decision (leave is usually refused without reasons, files are discontinued or settled), so tools built on decisions, CanLII included, never see them. One caveat: the docket is typed by Registry staff, so some entries contain errors, and any statistic inherits them.

iLit stores the court’s docket for all 316,940 immigration files. About 219,000 have already been turned into clear steps like these, and a newer, more detailed version is being tested on samples:

Working

File status in seconds

Enter a file number and see leave, judicial review result, judge, status and latest activity, fetched live from the court. Motions and stays are coming in the newer version.

Prototype

Who made the decision being challenged

CBSA, IRB, IRCC or a visa office, and the subject: removal, detention, inadmissibility, PRRA, H&C and more. A decision-maker was found for about 94% of a 1,000-file sample; accuracy not yet checked.

Would separate litigation about CBSA’s own decisions from the rest.

Prototype

Stays of removal

Stay motions and outcomes, with the scheduled removal date and destination when the docket states them.

New in the last few days, and so far tested on a 5,000-file sample rather than applied to the whole library: each file knows which steps apply at its stage (a file refused leave is no longer shown as “missing” a hearing), motion filings are linked to the docket entries they came from, and a repeatable test suite measures the docket reader. Motion types are still a prototype, identified for about a quarter of files in a sample.

This layer began as a Python version of the JRU Personal Inventory Tool, an Excel workbook for tracking one person’s caseload. iLit keeps its logic and scales it to every file in the court.

What makes it unique · 2

It makes citations smart

On CanLII a citation is a link. In iLit each citation knows where it sits in the decision, which paragraph it points to, and how it is used across the whole library.

What makes it unique · 3

AI gives every paragraph a meaning, and ties it to its authorities

Counting citations tells you what a court relied on. The next question is what each paragraph is doing: stating the issue, setting out the Minister’s position, applying a test, rejecting an argument. iLit uses rules and AI together to label each paragraph, then links it to the citations inside it.

This means an analyst can ask “show me every paragraph where a court applied the mootness test, and what it cited” and get the answer across the core decisions at once. A test search for “mootness” returned 25 paragraphs (the display limit), 33 citations and 21 linked authorities.

The AI layer is an early prototype. It has been run on 300 core decisions using a low-cost public AI service, at roughly a tenth of a cent per decision, and only on public court decisions.

Built to carry over · 1

The same engine is designed to work on the Division’s own material

Everything iLit does to a court decision (finding its citations, splitting it into paragraphs, linking each citation to the case it names and the paragraph it points to) works on ordinary text. That is deliberate. The same reader can be pointed at draft submissions, precedent memos and briefing notes, and connect them to the whole body of public case law.

Built to carry over · 2

It is designed to take in new cases as they happen

A research tool is only useful if it stays current. iLit was built from the start to add new decisions and new docket activity incrementally, not by rebuilding everything.

Built

Only what’s new

Every page is fingerprinted when stored, so duplicates are skipped. Processing steps such as indexing and tagging only handle items they haven’t done yet.

Built

Picks up where it left off

Overnight processing can be stopped and resumed safely, with a lock so two runs never collide. Collectors pull only recent months and stop if a site asks for human verification.

Next

Fully automatic

Today each run is started by hand, and a few hand-offs are manual (loading collected decisions, linking their citations). Joining those up and running it nightly needs an always-on machine.

Can it be relied on?

Every answer shows its work

Source first

The original decision and docket are kept untouched. Core facts keep a pointer to the sentence or docket line they came from.

Rules, not guesses

Core facts come from fixed rules that give the same answer every time. If something can’t be found, iLit says “not found”.

AI kept in its lane

AI adds labels in a separate layer. It never changes the source, the citations or the facts, and its labels are automatically checked against the source.

Built carefully

About 700 automated tests, dry runs before bulk changes, all-or-nothing database writes, and a written record of every change.

Collected politely

Public sources only. The Federal Court collectors space out their requests and stop if the site asks for human verification.

Can run in-house

Standard software and a local AI option, designed so nothing would need to leave the department once hosted there.

The foundation is built

The hard part is done: new intelligence can now be built on top

Most of the effort so far has gone into the base layers: collecting the data, keeping the originals, reading decisions and dockets into structured facts, and linking decisions, files and citations to each other. With those in place, new features are mostly a matter of asking new questions of data that already exists.

Already shown

Motion types, stage-aware file tracking and challenged-decision analysis were each added in days, because the docket data and the tests underneath were already there.

Within reach

Time from filing to leave decision by year and registry, stay success rates by type of removal, how often files are discontinued, and caseload trends by decision-maker. All can be derived from what is stored.

With local AI

Checking the Division’s own drafts against the case law, and summarizing how courts have handled each argument, once a capable model can run in-house.

“Within reach” items are not built yet. They are listed because the data they need is already in place.

Why independent, for now

Staying outside government is what lets it move this fast

Because iLit uses public information only, it doesn’t yet need approved hosting, a security assessment or a procurement process. That buys two things a departmental project rarely gets early on.

Flexibility

I can try an idea, test it on real data, and drop it the same week if it doesn’t work. Features like docket tracking, citation trends and paragraph meaning came out of that kind of trial and error.

Speed

Changes go from idea to working code in days, not quarters. More than 230 tasks have been recorded since early September; in the last two days alone the docket reader learned which steps apply at each stage of a file.

The trade-off is clear: it runs on my computer, it can’t touch internal documents, and nobody has vouched for it yet. Bringing it inside the department makes sense once it has proven itself, not before.

An unofficial funding idea

What a little money would buy

This isn’t a formal request. The project keeps going either way. Funding decides two things: how fast it moves over the next few months, and whether its AI can move onto a machine that could one day sit inside the department and read internal material.

Only an AI model that runs on a machine under the department’s control can ever be allowed to read internal documents. How good that model can be depends almost entirely on the machine’s memory.

Questions

Likely questions

Is this a chatbot giving legal answers?

No. The core is rule-based and repeatable, and every answer points to its source. AI only adds labels that are checked and kept separate. It is a research aid, not legal advice.

Why not just buy Westlaw or Lexis?

They would add general research, sold per user, but none of them tracks Federal Court files, codes Minister outcomes, or analyses immigration citation trends. iLit does, at the cost of a machine and some AI services.

Could it read the Division’s internal documents?

Not with a public AI, and it doesn’t today. With local hardware the AI runs inside the department, so internal documents can be analysed without leaving it, once that use is authorized.

How accurate is it?

In samples of up to 100 decisions, every recorded citation position matched the source text exactly. Automated AI reviews of about 480 decisions flagged 70–81% fewer citation problems after fixes. Neither is a human accuracy check. A hand-reviewed accuracy check of file tracking and outcomes is one of my next steps.

Who owns it?

It is a personal project, built on my own time with public data. If it were ever brought into the department, ownership and support would be settled then.

Why not bring it into government now?

It isn’t ready, and staying outside keeps it flexible and fast. It makes more sense to prove its value first, then look at hosting, security and internal documents.
