## Security risks

- **High — `side_projects/browser_game/tools/game_policy.py:38-53`; `side_projects/browser_game/tools/game_harness.py:99-113`**: The policy limits executable names and shell syntax, but then runs permitted Python/Node commands as ordinary subprocesses without an OS sandbox. For example, a Python `-c` argument can read files or use the network despite the README's stated boundary. Use an actual sandbox with filesystem and network restrictions; do not treat the argument checks as isolation.
- **High — `requirements.txt:24`; `backend/models.py:516-520`; `backend/routes.py:4261-4266`; `backend/embedding_providers.py:124-138`**: The current audit reports a model-code-execution advisory for `sentence-transformers==3.0.0` (CVE-2026-68770; fixed in 5.6.0). The local chunk-search endpoint accepts a caller-supplied model name and passes it to `SentenceTransformer`; an untrusted model identifier may therefore reach the affected loading path. Upgrade to a patched release and restrict model names to an approved set.
- **High — `requirements.txt:45,47`; `backend/resource_limits.py:85-100`**: `python-multipart==0.0.9` and `pypdf==4.2.0` have multiple current advisories, including denial-of-service risks when parsing attacker-controlled multipart/PDF inputs. The latest main-branch pip-audit report lists fixes at `python-multipart==0.0.31` and `pypdf==6.21.2`. Update and test the upload paths; existing size/page caps do not by themselves eliminate parser CPU or memory vulnerabilities.
- **Medium — `requirements.txt:8-9,39-40,50,54-55`; `requirements-dev.txt:1-7`**: The 2026-10-24 pip-audit run also reported vulnerable resolved versions: `starlette==0.37.2` (transitive; patched at 1.3.1), `requests==2.32.3` (2.33.0), `python-dotenv==1.0.1` (1.2.2), `pytest==8.2.2` (9.0.3), and `black==24.4.2` (26.10.1 for the newest listed advisory). It also reported transitive `transformers==4.57.6` advisories, with fixes varying up to 5.10.0 and at least one advisory with no fix listed. Review compatibility and update the dependency set. These are findings from the latest main-branch audit artifact, not an exploitability assessment.
- **Medium — `.github/workflows/tests.yml:21-23`; `.github/workflows/dependency-audit.yml:28-29,54`; `.github/workflows/docker-build.yml:44-50`**: GitHub Actions are referenced by mutable version tags (`@v4`, `@v5`, `@v3`). Pin third-party actions to reviewed full commit SHAs and automate controlled updates.
- **Medium — `Dockerfile:3,22`; `docker-compose.yml:8`**: `python:3.12-slim` and `pgvector/pgvector:pg16` are mutable image tags. Pin image digests (with a documented update process) for reproducible builds and to prevent a tag change silently changing the build.
- **Medium — `docker-compose.yml:41,52-53`**: The app port is published without a loopback host binding, unlike the database port, and `CASELIBRARY_ACCESS_PASSWORD` defaults to empty. On a host with a reachable network interface, this can expose an unauthenticated app beyond localhost. Bind the app to `127.0.0.1` for local use or require an explicit protected deployment configuration.

## Data-safety risks

- **High — `alembic/versions/0029_recent_5000_ivfflat_artifact.py:60-70,87,90-91`**: The migration uses `CREATE TABLE IF NOT EXISTS` and then runs `_REFRESH_SQL`, which truncates and repopulates the table. If that table already contains data, an ordinary schema upgrade destroys and replaces it. Keep migrations schema-only; move the refresh to a separately approved, dry-runnable job, or refuse to overwrite a pre-existing table.
- **High — `alembic/versions/0001_case_metadata.py:45-57,69-77`; `alembic/versions/0040_judge_profile_aliases.py:18-21,34-35`; `alembic/versions/0044_refined_pinpoints.py:24-41`; `alembic/versions/0045_issue_maps.py:20-24,54-60`**: Several upgrades skip columns/tables that already exist, but their downgrades drop those objects without recording whether this revision created them. For example, `0044` skips existing pinpoint columns and then drops all of them on downgrade; `0040` returns if its table exists and later drops it unconditionally. Similar guarded-create/unconditional-drop patterns occur in `0041`, `0042`, `0043`, `0046`, `0047`, and `0049`. Downgrading a database with pre-existing objects can delete unrelated schema and data. Track ownership of created objects or make such migrations explicitly irreversible rather than guessing during downgrade.
- **Medium — `alembic/versions/0003_backfill_processing_status.py:14-24`**: The upgrade changes `raw` to `embedded`, but the downgrade changes every embedded row with an embedding back to `raw`, including rows that may already have been `embedded` before this revision. Preserve the exact changed row set or make the downgrade a documented no-op.
- **Medium — `side_projects/luck_of_the_draw_iii/build_lotd_access_frontend.ps1:460-462`**: The builder deletes the existing `.accdb` before creating and populating its replacement. A later Access/CSV error leaves no working output. Build to a temporary path, validate success, then replace the old file.
- **Low — `alembic/versions/0008_case_provenance_tables.py:54-94`**: This schema revision also performs a full `INSERT ... SELECT` backfill from `cases`. It may add significant deployment time and its downgrade drops the copied rows with the table. Separate or explicitly document/size this data migration and provide a resumable path if the source table is large.
- **Low — `alembic/versions/0039_citation_refinement.py:106-109`**: The upgrade creates missing tables, but downgrade is a no-op. Downgrading leaves new schema behind. Record which objects the revision created, or clearly declare it irreversible and provide a safe cleanup procedure.

## Performance

- **Medium — `alembic/versions/0031_paragraph_similarity_postings.py:9-21`; `alembic/versions/0050_search_speed_indexes.py:23-28`; `alembic/versions/0001_case_metadata.py:45-65`**: These migrations build indexes without `CONCURRENTLY`; `0031` targets existing `case_chunks`, `case_tags`, and `citations`, and `0050` documents indexing 75,000 cases. On populated databases, index builds can block writes and hold substantial locks. Use concurrent index creation in an Alembic autocommit block where supported, or document and schedule the blocking deployment.
- **Low — `alembic/versions/0035_statute_library_phase1.py:21-40`**: `statutes.instrument_key` is declared `unique=True`, repeated as a `UniqueConstraint`, and receives a separate index. These create redundant indexes and increase migration/write cost. Keep one unique constraint/index and remove the duplicate.
