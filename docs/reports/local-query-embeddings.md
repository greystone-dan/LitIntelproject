# Local Query Embeddings

## Outcome

Query embedding provider selection is separate from answer generation.
`QUERY_EMBEDDING_PROVIDER` defaults to `none`: semantic and hybrid requests use
lexical ranking and do not invoke an embedding provider. Set it to `local` to
select the configured local SentenceTransformer query model; `openai` is an
explicit opt-in. `GET /api/search-embedding-status` reports the selected query provider,
model and output dimensions (null when disabled), indexed-vector dimensions,
whether query text leaves the machine, and the configured
`TEXT_GENERATION_PROVIDER`. Reading status does not instantiate an embedding
model.

This status describes where the query text is sent for embedding inference. It
does not claim that a local model is already installed: SentenceTransformer may
need to download model artifacts the first time it is used unless they are
already cached or supplied locally.

## Configuration

| Setting | Default | Purpose |
| --- | --- | --- |
| `QUERY_EMBEDDING_PROVIDER` | `none` | Disable query vectors by default; choose `local` or explicitly opt in to `openai`. |
| `QUERY_EMBEDDING_MODEL` | Provider default | Override the query model explicitly. |
| `QUERY_EMBEDDING_DIMENSIONS` | `1024` for local | Validate expected local model output size. |
| `TEXT_GENERATION_PROVIDER` | `openai` | Independently selects `/research` answer generation. |

For OpenAI, model selection falls back to `OPENAI_EMBEDDING_MODEL` and then
`text-embedding-3-small`. Local model selection falls back to
`LOCAL_EMBEDDING_MODEL` and then `BAAI/bge-m3`. Local inference uses
`LOCAL_EMBEDDING_DEVICE` (default `cpu`).

## Dimension and retrieval boundary

The standard semantic search path uses 1536-dimensional indexed vectors. Its
query embedding is checked against that contract before the vector is used in
retrieval. The default local BGE-M3 model returns 1024 dimensions; enabling it
for that standard path therefore produces a controlled dimension-mismatch
response, rather than an invalid vector query. Configure a query model and
stored-vector family that are compatible before using local queries for that
path. Equal dimensions alone do not establish that two embedding models share
the same vector space.

The model declarations in `backend/database.py` define three 1536-dimensional
vector columns and one 1024-dimensional model-versioned local chunk-vector
column. These are code-level schema counts, not counts of populated rows. The
standard query path searches the 1536-dimensional case/chunk vectors; switching
it to a 1024-dimensional model would require re-embedding the indexed corpus
with a compatible model and a coordinated schema/index migration. The number of
records to process is database-dependent and is intentionally not reported
here: no database was queried. Re-embedding also changes the vector space, so
all vectors compared in one retrieval path must be generated by compatible
models, even when dimensions already match.

The current change does not rewrite, backfill, or otherwise alter stored
embeddings. With provider `none`, semantic and hybrid requests fall back to
lexical search; explicit lexical-only search is unchanged.

## Latency expectations

Local inference removes the per-query embedding request to OpenAI, but it uses
the PC's local CPU or configured accelerator. The first query can take
substantially longer while the model is loaded, and may download model artifacts
if they are not cached. Warm-query latency depends on hardware, model, and query
length; it should be measured on the target PC before enabling local mode.
There is no fixed latency guarantee. Search retrieval and `/research`
generation have separate latency/provider paths.

## PC/cloud rollout plan

1. Keep query embeddings disabled while selecting a local model whose embedding
   space is compatible with the intended indexed vectors. BGE-M3's 1024
   dimensions do not match the standard 1536-dimensional path.
2. On the PC, confirm available disk, CPU/accelerator, local model cache, and
   measured cold/warm inference latency. Check `/api/search-embedding-status`
   before and after setting provider configuration; it reports configuration
   only and does not access model artifacts.
3. If the chosen model changes the indexed vector family, use the PC-side
   database and operations workflow to obtain live row counts, plan a reversible
   schema/index migration, and run a bounded, checkpointed re-embedding job.
   Do not mix old and new model vectors in the same search path.
4. Validate actual vector dimensions, model identity, and representative
   retrieval quality on the PC before enabling local queries. Verify that
   query text stays on the machine; first-use model downloads are separate
   outbound traffic.
5. Enable `QUERY_EMBEDDING_PROVIDER=local` only after compatibility is proven.
   Monitor latency and errors. To roll back query inference, restore
   `QUERY_EMBEDDING_PROVIDER=none` for local-only lexical search, or explicitly
   select `openai` if remote query embedding is acceptable; this does not undo
   any database migration or re-embedding.

## Validation and limitations

Provider selection, status reporting, and dimension failures are covered with
mock providers; tests do not download model artifacts or access a database.
The status response is configuration metadata, not a live connectivity check,
model-cache check, or proof of semantic compatibility. Query embedding is
disabled by default, OpenAI must be explicitly enabled, and
`TEXT_GENERATION_PROVIDER` does not implicitly select or change query embeddings.
